# 간결한 개발 판단 기록 구현 계획

> 실행: 승인된 설계에 따라 새 기능 브랜치에서 작업한다. 사용자에게 같은 설계를 다시 승인받지 않는다.

**목표:** 중요한 개발 판단과 실제 검증 근거를 짧은 MD로 남기는 선택형 작업 지침을 제공한다.

**구조:** 기존 Skill에 조건부 진입점을 넣고, Skill 내부 reference와 asset을 함께 배포한다. Python CLI와 JSON 형식은 유지한다.

**기술:** Markdown 지침·양식, 기존 Python 표준 라이브러리 회귀 테스트.

**설계:** [승인 범위와 기록 계약](../specs/2026-11-03-concise-development-log-design.md).

## 공통 제약

실제 과제·대화 기록 공개 금지, 작업 AI의 관찰 범위 표시, 소급 근거 생성 금지, 선택 기능의 지연 로딩, 기존 진행 보고와 CLI 쓰기 계약 유지. 공유 브랜치 병합·PR·릴리스는 별도 지시 대상이다.

## 작업 순서

1. 기준 버전과 테스트를 확인하고 분리된 작업 브랜치를 만든다.
2. 기록 안내와 빈 양식을 작성한다. 요약·주체·검증 출처·정정 이력·작업 위치를 명확히 한다.
3. README·BOOTSTRAP·Skill·관련 플레이북과 개발 명세에 필요한 연결만 추가한다.
4. 기존 회귀 테스트, 링크·길이·변경 범위, 깨끗한 복사본, 독립 Skill을 확인한다. 문구를 그대로 재검사하는 새 테스트는 추가하지 않는다.
5. 독립 리뷰와 제한된 합성 기록 작성 점검을 수행하고 실제 결과·미검증을 VALIDATION에 남긴다.
6. 실제 원격 기준 커밋을 부모로 하는 새 기능 브랜치에 반영하고 원격 파일·CI를 확인한다.

## 리뷰 초점

- 간결성: 요약과 중요한 이력으로 빠르게 읽을 수 있는가.
- 사실성: AI 제안과 사용자 결정, 직접 관찰과 사용자 보고를 섞지 않는가.
- 복구: 오래된 검증을 현재 PASS로 재사용하지 않는가.
- 호환성: CLI·기존 worklog·개발 현황의 계약을 유지하는가.
- 배포: 빈 양식만 공개되고 독립 Skill에도 필요한 파일이 포함되는가.
